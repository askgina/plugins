## Question

> What public evidence can establish correct state transitions across Uniswap v3/v4 and Raydium CLMM/CPMM?

## Answer

Public evidence can establish **what a correct transition must look like**. It cannot establish **that Gina performs it**.

Three kinds of public evidence exist, and none of them proves the others:

1. **Protocol source** at pinned official revisions ([Uniswap](#uniswap-sources) and [Raydium/Token-2022](#raydium-and-solana-sources)). These define identities, authority checks, state changes and events for each operation. From them we can build per-operation postcondition oracles.
2. **Chain RPC semantics** from Ethereum and Solana documentation. These define what a receipt or signature status proves: inclusion and execution outcome at a commitment level. They say nothing about whether the application-level intent was satisfied.
3. **The public Gina LP contract**: the guide and the pinned schema snapshot at `486bb0c`. It documents supported operation kinds, request identities (`intentId`, `quoteId`, `planHash`, `operationId`), recovery rules and the rule that "prepared, submitted and pending are not settled". The snapshot holds only **input** schemas for six tools. It has no execute-input or output schemas, status enums, receipt, transaction-list or asset-flow fields, approval-request IDs, or a field linking a recenter's retired and replacement legs.

`[INFERENCE]` A correct transition therefore needs evidence joined per operation: the confirmed plan; each transaction's receipt or signature status at a stated commitment; before and after position state keyed by protocol identity; and asset-flow reconciliation that separates principal, fees and rewards, transfer fees, wrap/unwrap, rent and gas. The reviewed public sources do not supply these joins or funded/deployed lifecycle evidence for a Gina operation `[MISSING PUBLIC PROOF]`; this is not a claim that such evidence cannot exist elsewhere. Every Gina row below is **documented, not proven**.

Key facts that should shape the matrix:

- **Recenter is composed in all three concentrated protocols.** None of the pinned official managers or programs changes an existing position's range. A recenter retires or drains the old identity and mints a new one (new tokenId or NFT mint). No protocol emits a "recenter" event that links the two legs. CPMM has no range, so recenter does not apply. `[PUBLIC CODE]`
- **Collect is not uniformly "fees only".**
  - Uniswap v3 `tokensOwed`, and so `collect`, mixes previously removed principal with fees.
  - Uniswap v4 has no collect action. Fees are credited by a zero-liquidity decrease. Hooks can adjust the deltas.
  - Raydium CLMM collect uses `DecreaseLiquidityV2` with zero liquidity: no principal is paid, because a nonzero decrease pays removed principal immediately and `token_fees_owed_*` accrues fees only. Enabled fee/reward paths pay owed amounts. A nonzero decrease pays principal plus all owed fees in one transfer per token; `DecreaseLiquidityEvent` reports them separately.
  - A nonzero CLMM decrease can succeed without removing liquidity when only the `DecreaseLiquidity` status bit is disabled and minimums are zero; the event `liquidity` field is the requested argument, so post-state liquidity must be read.
  - CPMM has no LP-user collect. Fees are embedded in reserves and realized through withdraw. `[PUBLIC CODE]`
- **A successful transaction can leave the intended effect incomplete.**
  - Raydium CLMM reward collection pays `min(owed, vault balance)` and can leave reward debt after success.
  - CLMM pool status bits can skip decrease, fee or reward subpaths within a successful call.
  - The Uniswap v3 manager `Collect` event emits the requested amount, which may exceed what was actually transferred by rounding.
  - Uniswap v4 `initializePool` swallows initialization failure. `[PUBLIC CODE]`
- **Confirmation and settlement are separate axes.**
  - An Ethereum receipt proves inclusion and a status (`1`/`0`), not finality.
  - Solana `sendTransaction` success does not mean the transaction was processed.
  - Solana `confirmed` and `finalized` are commitment levels, not application verdicts. `[PUBLIC DOC]`
- **Contract gaps and campaign overlays are not automatically contradictions.** Separate ratio swaps versus in-plan wrapping need attributable confirmation; the campaign's confirm-every-write rule is stricter than general product authorization language; schema unions do not establish protocol admission. Close composition and chain-specific observation windows still require evidence and case-oracle approval. See [Distinctions and outstanding tensions](#distinctions-and-outstanding-tensions).

### Chain settlement semantics

- **E1** `eth_getTransactionReceipt` returns `null` for pending transactions. A receipt carries `blockHash`, `blockNumber`, `logs`, `gasUsed`, `effectiveGasPrice` and `status` 1/0. Block tags `safe` and `finalized` are separate block parameters. ([ethereum.org JSON-RPC](https://ethereum.org/en/developers/docs/apis/json-rpc/#eth_gettransactionreceipt)) `[PUBLIC DOC]`
- **E2** Ethereum transaction lifecycle: inclusion, then "justified", then "finalized". ([ethereum.org Transactions](https://ethereum.org/en/developers/docs/transactions/#transaction-lifecycle)) `[PUBLIC DOC]`
- **S1** Solana transactions are atomic: if any instruction fails, all state changes revert, and fees are still charged. ([Transactions](https://solana.com/docs/core/transactions)) `[PUBLIC DOC]`
- **S2** A successful `sendTransaction` "does not guarantee the transaction is processed or confirmed". It can be dropped if the blockhash expires. ([sendTransaction](https://solana.com/docs/rpc/http/sendtransaction)) `[PUBLIC DOC]`
- **S3** `getSignatureStatuses` returns `confirmationStatus` (processed/confirmed/finalized) and `err`. A `null` entry means no status was found. Without `searchTransactionHistory` it searches only the recent status cache. ([getSignatureStatuses](https://solana.com/docs/rpc/http/getsignaturestatuses)) `[PUBLIC DOC]`
- **S4** `getTransaction` returns `meta.err`, `fee`, `preBalances`/`postBalances`, `preTokenBalances`/`postTokenBalances` (with `mint`, `owner`, `programId`, raw `amount`), `innerInstructions` and `logMessages`. `processed` is not accepted. ([getTransaction](https://solana.com/docs/rpc/http/gettransaction), [JSON structures](https://solana.com/docs/rpc/json-structures#transaction-status-metadata)) `[PUBLIC DOC]`
- **S5** Blockhash expiry: a blockhash is valid within 151 recent blockhashes, roughly 60–90 s. `getLatestBlockhash` returns `lastValidBlockHeight`. ([Confirmation & Expiration](https://solana.com/developers/cookbook/transactions/confirmation), [getLatestBlockhash](https://solana.com/docs/rpc/http/getlatestblockhash)) `[PUBLIC DOC]`
  - `[INFERENCE]` A `null` status means _not found_, not _failed_. For an ordinary recent-blockhash transaction, passing `lastValidBlockHeight` prevents future admission of those signed bytes; it does **not** prove they never landed. Even a history-enabled null response can reflect provider retention or coverage gaps. A non-landing conclusion needs covered history at the stated commitment and exact-signature identity; an operation-level zero-effect conclusion additionally needs all submitted/replacement signatures and legs covered plus attributable state/flow reconciliation. Missing EVM receipts likewise do not prove zero effect. These mechanics do not approve an observation window or resend.

### Recenter two-leg attribution

The public contract identifies the retired position through the quote input: EVM `position` or CLMM `nftMintAddress`/`positionAddress` (G9). The replacement identity exists only after execution:

- v3/v4: the new tokenId from the ERC-721 mint `Transfer`.
- CLMM: the new NFT mint and PDA.

The reviewed public snapshot supplies no output field, status row or per-leg transaction list linking retired and replacement identities `[MISSING PUBLIC PROOF]`. This input-only artifact cannot establish that deployed Gina lacks such fields. No single linking recenter event exists in the pinned standard protocol inventories; correlating exit and entry still needs operation/transaction attribution `[INFERENCE]`.

`[INFERENCE]` The evidence required is:

1. Operation ID bound to the confirmed quote.
2. The ordered leg list, with the transaction hash or signature and commitment of each leg.
3. The retired identity's post-state: L, owed amounts, burned or closed.
4. The replacement identity's owner, pool, range and L.
5. Per-currency flow: removed principal + fees/rewards + any preparation swap/wrap + fresh funding − redeposit − residual payout − transfer fees/rent/gas.

Whether the new position was funded by original capital or by fees is an accounting convention, not a protocol fact.

### Preparation and native funding

- Gina docs make ratio swaps **separate transactions** (G2). `[INFERENCE]` Separate transaction identity helps attribution, but does not alone bind a swap to an LP intent or prove campaign confirmation.

## Distinctions and outstanding tensions

These are evidence distinctions and unresolved case-oracle gates, **not a finding of mutually contradictory product documentation**. No policy alternative is selected here.

1. **Preparation shape and attribution.** `[PINNED SNAPSHOT]` Ratio swaps are separate transactions; compiler-supported WSOL wrapping is disclosed through `wrapsNativeSol` (G2). `[INFERENCE]` Those are different preparations, not incompatible statements. [#154](https://github.com/askgina/plugins/issues/154#issuecomment-5915159678) now locks bounded swap/wrap preparation into the pilot, subject to every-write confirmation and campaign limits. `[MISSING PUBLIC PROOF]` An actual quote, instruction/transaction breakdown and attributable flows must establish what an in-plan wrap does and which exact write approval covers it; the remaining gate is this case contract and evidence, not whether preparation is permitted in principle.
2. **Authorization overlay.** `[PINNED SNAPSHOT]` A complete imperative request authorizes preparation/execution in general product usage (G8), while a quote alone does not authorize execution (G3); these describe different inputs and are compatible. `[PUBLIC DOC]` #154's confirm-every-write rule, including preparation/cleanup, is the stricter campaign overlay. General product authority cannot waive it. The wording does not create an unresolved owner decision to reconcile two contradictory docs.
3. **Close semantics and composition.** `[PINNED SNAPSHOT]` The guides distinguish Uniswap remove/collect from CLMM empty-position closure (G1/G6). `[INFERENCE]` "Remove all & close" does not by itself prove NFT destruction, atomicity, transaction count or zero reward debt. Protocol requirements differ: v3 burn requires L/owed = 0 (U3), v4 burn can remove L (U8), and CLMM close requires every fee/reward debt = 0 (R7). `[MISSING PUBLIC PROOF]` Exact quote legs and resulting state must establish the campaign's approved close oracle; partially paid CLMM rewards can block closure without a failed transaction (R6).
4. **Schema representation versus runtime validation.** `[PINNED SNAPSHOT]` The Solana input schema exposes a broad operation-kind enum and pool union, while the support matrix limits CPMM to deposit/withdraw; the snapshot expressly omits full refinements (G9). `[INFERENCE]` A union admitting a shape is not evidence that protocol validation accepts it and is not inherently a documentation contradiction. `[MISSING PUBLIC PROOF]` Execute-input and output schemas are absent, so `planHash`, `expiresAtSlot`, wrap disclosure, status words/enums, receipt/transaction/flow fields, approval identity and recenter linkage have no published schema in this input-only snapshot. Several are described in guide prose; absence here does not prove runtime absence or establish deployed shape. No Solana `quoteId` appears in the Solana status input, but **its absence from status input does not establish absence from execute**. UUID-versus-string status IDs are a represented difference, not a contradiction.
5. **Observation versus inherited bounds.** `[PUBLIC DOC]` #154 locks the requirement to research and then approve bounded chain-specific read-only windows, with writes frozen during uncertainty and explicit owner recovery/resumption after missed cleanup deadlines. It approves **no exact windows**. `[INFERENCE]` Neither the inherited #69 limits nor the product FAQ's 20 s swap receipt check nor Solana's approximate 60–90 s recent-blockhash validity selects an LP settlement/finality window. Exact observation/cleanup bounds remain a campaign gate; no replacement is chosen here.
6. **Protocol documentation scope.** `[INFERENCE]` Generic Token-2022 or reward terminology does not establish support for a particular Raydium instruction, deployment or Gina plan.
