# Publicly testable Predictions MCP workflows

Research for [Research publicly testable Predictions MCP workflows](https://github.com/askgina/plugins/issues/67), part of [Spot, Perps and Predictions MCP evaluations](https://github.com/askgina/plugins/issues/65). Public documentation read on September 9, 2026.

## Question and evidence boundary

Which Predictions workflows and correctness oracles can distinguish the intended event, market, outcome, and time window from superficially similar results?

This file inventories public capabilities and drafts two-layer candidate cases. It is not a measured evaluation. No model or MCP calls, account access, trades, redemption, automation changes, tests, or formatting commands were run. Documented capabilities do not establish current availability or authorize execution. The word sandbox describes the MCP workspace, not simulated finances. Trading on this connection uses real USDC on Polygon. [Trading][trading], [FAQ][faq]

Public evidence is limited to docs.askgina.ai and public askgina/plugins issue text. Dedicated Predictions MCP pages are primary. Gina Read, the access comparison, and web-app Predictions/scheduling pages are adjacent product guidance. They support domain distinctions, not dedicated MCP action names, response schemas, or runtime success. Gina Read's named research catalog is a different MCP surface and must not be treated as Predictions MCP host-tool names. [Spot, Perps and Predictions MCP evaluations](https://github.com/askgina/plugins/issues/65) already states that the existing four-case Gina Read smoke is not a venue acceptance matrix.

The venue evaluation map requires separate deterministic contract/safety checks and natural-language agent trials. Neither substitutes for the other. Precise model, auth, and pinning choices remain on [Specify cross-provider result identity and evidence semantics](https://github.com/askgina/plugins/issues/49) and [Choose runner authentication and isolation policy](https://github.com/askgina/plugins/issues/51). Safety, grading, admission, and acceptance decisions remain open; the owner has already selected all three dedicated MCPs and two evaluation layers.

## Documented access and discovery boundary

- Predictions MCP exposes one MCP tool, `bash`. Prediction operations run through `host-tools` inside its sandbox. Host-tool actions must not be counted as separately advertised MCP tools. [Introduction][intro], [Access][access]
- This is dedicated write access, requesting `tools:execute` at `https://askgina.ai/ai/predictions/mcp`. Credentials must be valid for that venue; a read-only token or old Gina execute grant is not a substitute. OAuth connection approval is distinct from the user's intent for a particular task. Gina Read cannot trade or create schedules, and research access cannot place or cancel orders or redeem positions. [Client setup][setup], [Access][access], [Read Predictions][read]
- A request to prepare or quote differs from a request to execute. Feature pages still describe user prompts in natural language with no special syntax. [Access][access], [Features][features]
- Public troubleshooting documents help discovery through `commands --help host-tools`, detail discovery through `host-tools --name searchPredictionMarkets --limit 5 --full`, and execution of the search action with a JSON argument containing `query`. These are evaluator-side reference facts, not commands to embed in agent prompts. `searchPredictionMarkets` is the only host-tool name those pages publish. Buy, sell, cancel, redeem, position, SQL, and schedule action names remain unknown. The page promises tool details, not a fixed complete input/output schema or stable allowlist. [Troubleshooting][trouble]
- The FAQ describes search/list/trending as read-only and says large trading orders require explicit confirmation. It does not define "large," universal confirmation behavior, or a confirmation receipt. Trading documentation separately tells users to review details before confirming. An evaluation must not assume a second confirmation protects every write. [FAQ][faq], [Trading][trading]

## Two-layer candidate matrix

These are proposals, not locked acceptance criteria. Layer 1 uses controlled evidence to test declared invariants. It cannot become a deterministic MCP wire-contract suite until the relevant public contract or separately admitted schema evidence exists. Layer 2 asks an agent to satisfy a user goal. Keep evaluator fixtures, expected identities, tool details, and grading rules outside the user prompt.

For every proposed case, the evaluator should separately record the connection/runner identity, source or fixture version, observation time, scenario clock/timezone, account prerequisites, and authorized action ceiling. These are proposed evaluation metadata, not claims about fields returned by Predictions MCP. Synthetic, recorded-response, and live evidence must be labelled separately. No live evidence was collected here.

[Discovery][discovery], [Portfolio][portfolio] |
| C4 | Wrong book side, stale quote, valid empty result, unavailable/partial data | Controlled evidence distinguishes these states. | C7 | Pending/part-filled order, cancel race, resolved winner awaiting redemption | Declare these states in controlled evidence; partial fills and races are proposed adversarial fixtures, not documented native status variants. ### Layer 2: natural-language agent task candidates

Prompts below are goal-only drafts. Relative dates and phrases such as "this market" require an evaluator-supplied clock and prior conversational context. Write-intent rows are planning examples, not authorization to execute them.

| ID | Candidate user request | Confusion pair and evaluator-side evidence |
| --- | --- | --- |
| A1 | "Find this weekend's Premier League match markets and compare the home teams' chances." | Match winner versus league champion, wrong game/date, missing draw. C2/C3/C4. Match rules, outcomes and zoned dates to the request; disclose unavailable prices. [Discovery][discovery], adjacent [Read Predictions][read] |
| A1b | "For the match we just opened, I only care who wins. Ignore extras." | Winner versus first-to-score, halftime, corners, exact score, or spread on the same fixture. C2/C4. Adjacent Gina Read shows those extras as grouped markets, not as dedicated MCP fields. [Read Predictions][read] |
| A2 | "Which political markets are getting the most attention, and which are ending in the next two hours?" | Trending versus volume versus expiry. C3/C4. Preserve separate criteria and time window; explain absent ranking/freshness evidence rather than inventing it. [Discovery][discovery] |
| A3 | "Find the next fifteen-minute Bitcoin up-or-down market and tell me when it closes in London time." | Current versus next, fifteen-minute versus hourly, local timezone versus UTC. C2/C3. Fixture identifies the occurrence, rules and interval; permit clarification if "next" is unresolved. [Discovery][discovery] |
| A4 | "Compare Apple's next daily direction market with Netflix's weekly price targets." | Daily up/down versus weekly multi-strikes; wrong session or strike. C2/C3/C4. | A5 | "For the outcome we just chose, what would buying $40 actually cost at the available prices? Don't place an order." | Displayed odds versus book liquidity/execution cost; wrong outcome/side. | A7 | "Explain the risk of spending $25 on Yes in this market. I haven't decided whether to buy." | Proposal versus execution; dollars versus shares. C2/C6. Resolve market/outcome from context, preserve budget units and describe loss/payout assumptions without trading. [Trading][trading], adjacent [Web Predictions][web] |
| A8 | "Buy $25 of Yes in the market we selected, with a maximum price of 40 cents per share." | Dollar budget versus 25 shares, buy versus sell, limit versus guaranteed fill. C2/C6/C7. | A12 | "Rank this week's crypto markets by volume, then show which odds moved by more than ten percent yesterday." | Snapshot versus history, price-relative percent versus percentage points, complete catalogue versus fetched subset. | A14 | "Did my morning briefing run? Pause that briefing, but keep my other alerts." | Scheduled/queued versus completed; pause versus delete; specific versus all. C6/C9. Controlled account, identified automation and run evidence; distinguish unavailable status from a failed run. Deletion needs a separately explicit request. [Advanced][advanced], adjacent [Schedules][schedules] |

Each suitable row should also have a valid-empty and unavailable-data variant. An empty portfolio, missing account access, provider failure and partial response are distinct evaluator states. These variants are proposed evidence conditions, not assertions that the public MCP exposes standardized status fields for them.

## Available observations versus missing oracles

Available from public sources, as documentation rather than live proof:

- Connection identity: dedicated Predictions URL, `tools:execute`, MCP `bash`, in-sandbox `host-tools`. [Setup][setup], [Access][access], [Introduction][intro]
- Operator smoke: echo, host-tools help, named search-tool details, search with `query`. [Troubleshooting][trouble]
- Advertised workflows and NL examples for discovery, trading, portfolio, SQL, and automations. [Features][features]
- Binary Yes/No payout illustration, real USDC on Polygon, resolve-and-win redemption, open/pending orders. [Trading][trading], [Portfolio][portfolio]
- Recurring crypto asset/timeframe table and stock/index/gold examples. [Discovery][discovery]
- Adjacent identity, timezone, close-versus-resolution, proposal-versus-execute, and queued-versus-complete guidance. [Read Predictions][read], [Web Predictions][web], [Access][access], [Schedules][schedules]

Missing from public sources, and therefore unknown unless later admitted:

- Host-tool names beyond `searchPredictionMarkets`, complete input/output schemas, stable allowlists, and wire errors
- Event/market/outcome identifiers, slug mapping, series versus event versus market identity
- Timestamp timezone, window-boundary inclusivity, ranking formulas, freshness, empty-versus-unavailable fields
- Dedicated book action, depth format, executable-price semantics, and quote timestamps
- Funding/allowance prerequisites, confirmation threshold, proposal objects, fill/cancel/redemption receipts, partial-fill fields, and settlement proof
- P&L, win-rate, and volume definitions; SQL production schema and history completeness
- Automation trigger, timezone, run-status, and delivery evidence on the dedicated MCP
- Runtime availability, account data, and any observed receipts

A successful documented command, a sandbox, or a closed market is not an oracle for settlement, dry-run money, or resolution.

## Open owner decisions

1. **Identity and clarification policy.** Choose the minimum admissible identity/rules evidence, how prior conversational selection is bound, and when ambiguity requires a question instead of a best-effort selection. Public titles and examples alone cannot decide this.
2. **Time oracle.** Define "next," "today," expiry inclusion, reporting periods, timezone defaults, daylight-saving transitions and stock-session calendars. Keep close time, resolution time and redemption eligibility separate. Set a freshness threshold instead of treating a screenshot or old quote as current.
3. **Admitted schemas and evidence.** Decide how runtime-discovered action contracts may later be captured and versioned, which book/status/receipt evidence is required, and how missing fields are graded. Until then, schema-dependent contract checks remain candidates, not ready acceptance gates. Unsupported evidence should produce an ungradable or insufficient-evidence outcome, not fabricated success.
4. **Execution and account boundary.** Choose safe account fixtures, funding/allowance prerequisites, trade and redemption caps, local SQL write permissions, automation permissions, and confirmation expectations. Do not rely on the FAQ's undefined large-order threshold. This research grants no live-write authority.
5. **Pending, partial and final-state grading.** Select authoritative readback, bounded waiting and retry policy for fills, cancellation, redemption and schedules. Decide when an honest pending result satisfies the task and when finality is required. Do not retry an uncertain mutation merely to obtain a cleaner answer.
6. **Analytics definitions.** Fix win-rate denominator, P&L period/fee treatment, volume units, SQL history completeness, and percent versus percentage-point changes. Do not reward a plausible number whose inputs or definitions are unavailable.
7. **Scheduling evidence.** Specify account availability, cadence/trigger semantics, pause/delete identity, delivery target and proof of completion. The web-app guide is not a promise of dedicated MCP lifecycle fields.
8. **Runner and acceptance ownership.** Reuse [Choose comparison claims and the initial evaluation matrix](https://github.com/askgina/plugins/issues/47), [Specify cross-provider result identity and evidence semantics](https://github.com/askgina/plugins/issues/49), and [Choose runner authentication and isolation policy](https://github.com/askgina/plugins/issues/51) as directed by [Spot, Perps and Predictions MCP evaluations](https://github.com/askgina/plugins/issues/65). Owners still need per-layer pass criteria, weights, supported profiles and evidence-publication approval. Do not reopen the completed investigation attached to [Track intermittent OMP MCP-error observation loss](https://github.com/askgina/plugins/issues/63), or treat the existing Gina Read smoke cases or controlled fixtures as dedicated venue coverage.
